# 개발 계획

세로형 2D 모바일 **청소회사 경영시뮬레이션**을 개발합니다. 직원은 자동으로 작업하고 플레이어는 의뢰, 인력·장비와 거래 조건을 판단합니다. 첫 버전에서는 **의뢰 선택 → 팀 배치 → 자동 작업 → 손익 확인**을 먼저 검증합니다.

## 현재 상태와 구분

- 게임명, 2D 그래픽, 세로형 화면과 승인된 아트 기준을 유지합니다.
- 기존 방치형 성장 중심 계획을 청소회사 경영 중심으로 변경합니다.
- 원본 PNG 3종과 게임 콘셉트·아트 기준·개발 계획을 보관합니다.
- `prototype/`에는 경영 규칙을 확인하기 위한 브라우저 시제품을 둡니다.
- 최종 모바일 게임의 제작 엔진·언어·출시 순서는 아직 확정하지 않았습니다.

브라우저 시제품의 임시 그래픽·수치는 규칙 검증용입니다. Android 빌드나 최종 아트가 적용된 게임 완성본을 뜻하지 않습니다. 이전의 Godot + GDScript, Android 우선 추천은 제안으로 남으며 확정된 선택으로 간주하지 않습니다.

## 첫 시제품의 검증 목표

1. 현장 물량을 보고 의뢰와 초기 팀 구성을 고를 수 있는가?
2. 세척·운반의 막힘이 현장에서 보이고, 재배치로 이를 개선할 수 있는가?
3. 예상과 실제 이익이 달라진 이유를 이해하고 다음 판단을 바꾸고 싶어지는가?
4. 운영 손실 후에도 복구 의뢰를 통해 다시 시도할 수 있는가?
5. 청소 전후 변화와 서로 다른 현장이 다음 플레이의 동기가 되는가?

기존에 제안한 약 10분 체험은 초기 플레이 검토의 참고값으로 남깁니다. 세션 길이 제한이나 출시 기준을 뜻하지 않습니다.

## 첫 버전 범위

| 항목 | 경영 규칙 시제품 범위 |
| --- | --- |
| 의뢰 | 안정적인 야영지, 세척 물량이 많은 욕탕, 운반 물량이 많은 유물고, 복구 의뢰 |
| 인력 | 총 4명을 세척·운반에 배치, 각 역할 최소 1명 |
| 장비 | 수레·세척기 현장별 임대, 해당 의뢰에 장비비 반영 |
| 자동 작업 | 세척 → 적치 → 운반, 적치량에 따른 작업 막힘 |
| 진행 속도 | 1배·4배 보기, 배속에 따른 손익 변화 없음 |
| 운영 조작 | 의뢰 수락 전 배치, 작업 중 역할 재배치 |
| 현장 표현 | 직원 동작, 세척·운반 진행과 적치물, 청소 전후 변화 |
| 정산 | 초기 배치의 예상 시간·이익, 실제 시간·이익, 비용과 차이의 원인 |
| 손실 대응 | 공개된 비용·물량의 운영 위험, 복구 의뢰로 재시도 |
| 자동 수주 | 다음 의뢰는 플레이어가 직접 선택 |

시제품의 위험은 운영 선택에서 발생하는 손실로 한정합니다. 무작위 사고, 유물 소유권 협상, 단골과 평판은 포함하지 않습니다. 영구 장비 구매, 추가 고용과 직원 육성도 후속 범위입니다.

작업 비용은 작업에 소요된 게임 내 시간만 계산합니다. 완료 후 대기 시간이나 단순히 정산 화면을 보는 시간에는 인건비를 추가하지 않습니다. 초기 배치를 유지하면 예상과 실제가 일치하며, 작업 중 재배치하면 시간과 손익이 달라질 수 있습니다. 저장·오프라인 진행은 기본 흐름을 검토한 뒤 별도 범위를 정합니다.

## 단계별 구현과 검토

### 1단계 경영 규칙 시제품

순수 JavaScript 브라우저 시제품으로 의뢰 비교, 팀 배치, 현장별 장비 임대, 자동 작업과 재배치, 손익 정산을 연결합니다. 세척·운반의 병목과 인건비 계산을 독립 규칙 모듈에서 처리합니다.

확인할 결과: 같은 인원이라도 의뢰의 물량에 따라 유리한 팀 구성이 달라지고, 재배치가 작업 시간과 이익에 영향을 주는 반복 가능한 경영 흐름.

규칙 테스트에서는 아래 사항을 확인합니다.

- 세척·운반 처리량이 총 물량을 넘지 않고 완료 시점이 일관되는가?
- 적치 공간이 차면 세척이 막히고, 운반으로 다시 진행되는가?
- 현장 물량·장비·인력 구성에 따라 시간과 손익이 달라지는가?
- 완료한 현장의 비용이 계속 증가하지 않는가?
- 같은 운영은 1배·4배 진행에서 같은 작업 시간과 손익을 내는가?
- 손실 이후에도 복구 의뢰를 이용할 수 있는가?

### 2단계 짧은 플레이 검토

플레이어에게 의뢰 비교와 현장 관찰, 재배치, 정산을 경험하게 합니다. 설명을 따라 정답을 누르는지를 넘어 스스로 원인을 읽고 다른 운영을 시도하는지 봅니다.

관찰할 행동과 질문:

- 보상을 받기 전에도 청소 장면을 보고 있는가?
- 인력을 바꾼 이유와 결과를 설명할 수 있는가?
- 정산을 본 뒤 다음 의뢰나 팀 구성을 바꾸는가?
- “다시 한다면 뭘 하고 싶어?”에 다음 현장이나 다른 조합을 언급하는가?

접속 보상과 성장 수치에 대한 반응만으로 기본 경영의 재미를 통과시켜서는 안 됩니다. 청소 쾌감의 소리·동작과 최종 아트 완성도는 브라우저 규칙 검증과 별도로 검토합니다.

### 3단계 제작 엔진과 세로형 아트 구현

규칙과 플레이 검토 결과를 바탕으로 엔진·언어·첫 실행 기기를 확정합니다. 승인된 밝은 판타지 배경, SD 직원과 목재·양피지 UI를 적용하고 청소 전후 변화를 다듬습니다.

확인할 결과: 휴대폰 화면에서 현장의 문제와 조작부가 읽히고, 직원 동작·소리·바닥의 변화가 청소 과정의 만족감을 전달하는 버전.

### 4단계 회사 운영의 확장

기본 경영이 재미있어진 뒤 직원 고용·육성, 영구 장비 구매, 회사 공간 성장, 저장·오프라인 진행을 확장합니다. 현장 임대와 영구 투자를 구분하고, 복귀하면 작업 결과와 다음 판단이 보이도록 합니다.

확인할 결과: 회사가 성장하더라도 현장마다 선택의 의미가 유지되고, 플레이어가 정한 운영 방침이 자동 작업에 반영되는 버전.

### 5단계 거래와 세계의 확장

보수와 회수품 소유권을 비교하는 계약 조건, 단골과 평판, 새로운 현장과 발견을 연결합니다. 직원 성격, 복원한 공간과 주민의 귀환 등 애착을 만드는 콘텐츠도 이 단계에서 검토합니다.

확인할 결과: 단기 수익뿐 아니라 다음 거래와 회사의 방향을 고려하게 되는 장기 경영 흐름.

각 단계의 일정과 완료 날짜는 정하지 않았습니다. 후속 기능을 늘리기 전에 앞 단계에서 관찰한 문제가 해결되는지를 확인합니다.

## 실행과 규칙 테스트

바로 플레이하려면 `prototype/play.html`을 브라우저에서 엽니다. 소스를 변경한 뒤에는 `node prototype/build.mjs`로 단일 파일을 다시 생성합니다.

저장소 루트에서 실행합니다.

```bash
python3 -m http.server 8765 --directory prototype
```

[http://localhost:8765/](http://localhost:8765/)에서 시제품을 열 수 있습니다.

```bash
node --test prototype/engine.test.mjs
```

테스트 통과 여부와 실제 브라우저 플레이 결과는 실행 후 확인합니다. 이 문서의 검증 항목은 완료 보고나 통과 수치를 뜻하지 않습니다.
